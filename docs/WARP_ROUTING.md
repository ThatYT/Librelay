# Persistent WARP routing in Protocols

The Protocols page has a **WARP routing** button in its toolbar and on each VPS
card. Choose a VPS, enable routing, review the local SOCKS port and domain
suffixes, then select **Save and apply**. The button is available before creating
protocols and for nodes that only have relay protocols through the toolbar.

Defaults match the earlier VMISS deployment:

- Disabled until explicitly enabled; existing nodes retain current behavior.
- SOCKS5 endpoint: `127.0.0.1:31000` (port editable; loopback address fixed).
- Domains: `google.com`, `google.com.hk`, `googleapis.com`, `gstatic.com`,
  `googleusercontent.com`, `notebook.google`, including subdomains.
- Matching TCP uses WARP; matching UDP is rejected, allowing clients that support
  it to fall back to TCP. Applications requiring UDP will fail for these domains.
- WARP failures do not silently fall back to the native exit.
- Hostnames go through SOCKS for remote resolution. IP-only destinations do not
  match this policy. No global DNS, interface or default-route changes are made.

WARP must already be installed and connected in local proxy mode on the VPS.
This option manages sing-box routing; it never installs/registers WARP or changes
its service automatically. **Test WARP** performs a read-only HTTPS Cloudflare
trace request through the selected VPS's loopback SOCKS port, requiring
`warp=on` or `warp=plus` and a valid exit IP. It does not change routing settings.
Failed checks show copyable commands for manual installation/configuration using
the official signed Cloudflare APT repository on supported Debian/Ubuntu versions.
The commands use proxy mode, the selected port and retain an existing registration;
review Cloudflare's terms before running the displayed `--accept-tos` commands.
An unavailable/older node agent is reported separately from an unhealthy proxy.
A successful check verifies the proxy, not any application's route through it. **WARP configured** describes the
saved policy, not a live WARP connection check.

## Persistence and routing order

The policy is stored as JSON in nullable `node.warp_routing`. Startup migration
adds only this column when absent; it never resets data or regenerates credentials.
Fresh databases include the same column. All normal node config pushes read the
current saved policy through `NodeCommandClient`, so protocol creation, deletion,
port changes, assignment/revocation and manual pushes retain it.

Public mode remains:

```text
protocol authentication -> per-user GOST meter -> sing-box private gateway
  -> matching TCP: WARP
  -> matching UDP: reject
  -> other destinations: existing direct/landing route
```

Legacy protocols apply the rules to their protocol inbound after public GOST
forwarding has already metered the traffic. Gateway tags are derived from current
inbounds, not copied from a previous deployment. Routing applies to all protocols
on the selected VPS, including relay protocols. Matching domain rules take priority
over the landing outbound. Unmatched traffic keeps its existing landing/direct route.
The public per-user routes and rejection of unmetered traffic stay ahead of the
TCP WARP route; WARP cannot bypass them. Named matching UDP is also rejected at
the authenticated public inbound before GOST can resolve away its hostname.

The private GOST SOCKS connector explicitly uses standard UDP relay (`relay=udp`)
when talking to the sing-box gateway. Its previous default used a proprietary
UDP-over-TCP extension unsupported by that gateway; the real unrelated-UDP test
exposed this compatibility issue. This correction is generated by the backend
and does not require changing the node executable.

**Save and apply** persists desired settings before requesting a node push. If
applying fails or the node is offline, the response explicitly says settings were
saved but not applied. Retry **Resend configuration** after fixing the node. The
agent's existing candidate-validation/restart handling remains unchanged. Invalid
stored policy blocks a push instead of silently removing the WARP route; reopen
WARP settings and save a corrected policy.

Disabling the option and successfully pushing removes only generated WARP
outbound/rules, restoring the configured direct/landing paths. This does not stop
or uninstall WARP. Do not restore a whole historical sing-box backup over newer
protocol/user settings.

## Validation and deployment

Focused tests cover policy normalization, disabled compatibility, persistence on
repeated pushes and port edits, rule ordering, public/legacy HY2/TUIC, and offline
save behavior. The MySQL CI fixture checks additive migration and retained policy.
A local mock-API browser preview checks the settings dialog and save/reopen flow.
Frontend form/localization tests, TypeScript checking and a production build are
included in validation.

Optional runtime tests use actual Java-generated configs, sing-box 1.13.12 clients
and servers, and real GOST meters/UDP forwarders. A disposable local SOCKS proxy
stands in for WARP. They verify hostname delivery, matched/unmatched routing,
authentication, accounting, matching UDP rejection, unrelated UDP forwarding,
proxy failure without native fallback, and preservation after a server restart. No production VPS or Cloudflare daemon is modified.

Local validation passed on macOS arm64: 24 focused Java tests, eight frontend /
localization tests, TypeScript checking, a production frontend build, and four
real HY2/TUIC public/legacy runtime paths with sing-box 1.13.12. Existing private
GOST egress and user-limit checks also passed. CI runs the MySQL migration test
and the protocol runtime checks on Linux.

To reproduce after preparing a disposable certificate/key and sing-box executable:

```sh
mvn -B -f springboot-backend/pom.xml \
  -Dtest=WarpRoutingTest,WarpRoutingServiceTest,RealityPortTest \
  -Dlibrelay.warp.fixtures=/tmp/warp-fixtures \
  -Dtms.singbox.cert=/absolute/path/self.crt \
  -Dtms.singbox.key=/absolute/path/self.key test
(cd go-gost/x && LIBRELAY_SINGBOX_TEST_BIN=/absolute/path/sing-box \
  LIBRELAY_WARP_FIXTURES=/tmp/warp-fixtures \
  go test ./socket -run TestWarpRoutingPaths -count=1 -v)
```

Deploy the updated **backend and frontend** together. An agent update is required for the new **Test WARP** command; routing itself
continues to work with the existing configuration command. On VMISS, enable the policy with port `31000`, then verify an actual
client request and repeat after a normal panel config push. Existing subscriptions
and credentials do not need refreshing. Config application restarts sing-box and
may interrupt active connections.

This work does not deploy a VPS or publish a release. Main-push workflows currently
publish images and node/Android prereleases, so the PR remains unmerged under the
existing no-release constraint.
